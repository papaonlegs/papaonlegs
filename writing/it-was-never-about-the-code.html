It was never about the code

Summary — 10 reasons why your vibe coded app won't scale · Farouk Umar

Not one of the ten reasons in this series is an AI problem. Every one is what happens when software gets written without anyone making a decision. Vibe coding didn't invent these failures — it removed the friction that used to force you to confront them. Typing the code slowly was never the value. Being made to think while you typed was.

The ten, one line each

  • 1 — Six data models, one user. Every prompt invents its own domain model, because nothing persists the last one.
  • 2 — 40ms locally, 40 seconds in production. Small test data hides every N+1 query until real traffic finds it.
  • 3 — The login page is a prop. Auth built for the UI a human clicks, not the API an attacker curls.
  • 4 — Authorisation is a vibe. Forty handlers, forty interpretations of who's allowed — and RLS never turned on.
  • 5 — Your frontend talks straight to the database. Every secret in the client bundle is a secret an attacker can read.
  • 6 — Nothing is idempotent. Retries are infrastructure's default behaviour; duplicate handling was never built for them.
  • 7 — It works on one box. State that lives in memory disagrees with itself the moment a second instance exists.
  • 8 — You can't see it either. No memory of writing it, no telemetry to replace that memory.
  • 9 — Profitable at 100, bankrupt at 10,000. Flat pricing meets a cost curve that scales with usage, not revenue.
  • 10 — The bus factor is zero. The theory of the system lived in a prompt, and the prompt is gone.

The pattern underneath all ten is the same: every item is a deferred decision. Deferred decisions accrue interest quietly, the way unaddressed technical debt always has — and scale is simply the moment the loan gets called in. None of this is new to software. What's new is the volume: it's now possible to defer a year's worth of these decisions in an afternoon, faster than any team can review them.

The honest counterweight has to be genuine here, or the whole series reads as a sneer at a genuinely useful way of building. The speed is real. Most projects die from never shipping at all, not from scaling badly — a fast, ugly path to a working product beats a slow, clean path to nothing every time. The error isn't using these tools. It's treating speed and leverage as the same thing, when they're not: speed gets you to a working version faster; leverage is what determines whether that version survives contact with real users.

The practical split is between decisions that must be authored — by a person, deliberately, in one place — and everything that can safely be generated. The authored list is short and specific: the domain model, the auth model, the authorisation policy, the trust boundary between client and server, the idempotency strategy, the migration strategy, the cost model. Almost everything else — the CRUD handlers, the UI, the routine glue code — is exactly what these tools are good at, and generating it is not the mistake. The mistake is letting the short list get generated by default because nobody stopped to notice it was on the list at all.

Ten questions, one per post, worth running through before anything you've built this way meets real traffic:

  1. Can you say, in one place, what a "user" is — and is it the only place?
  2. Do you know how many queries your busiest endpoint makes per request?
  3. If a session token leaked today, could you revoke it?
  4. Can you show the policy that decides who sees what — without grepping handlers? Is RLS on?
  5. What can an attacker reach with nothing but the keys in your JS bundle?
  6. What happens when your payment webhook is delivered twice?
  7. What breaks when you go from one instance to two?
  8. Can you follow a single user's request across your whole system by one ID?
  9. What does one request cost you — and who can make 10,000 of them?
  10. Can you explain how it works? Then why did you merge it?

If you've shipped fast with AI tools and want a second pair of eyes before it goes further, that's exactly what a vibe code audit is for.
