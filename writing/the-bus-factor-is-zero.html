10 — The bus factor isn't one, it's zero

Part of 10 reasons why your vibe coded app won't scale · Farouk Umar

The dangerous version isn't that only one person understands the system. It's that nobody does — including the person who shipped it.

Peter Naur's 1985 essay Programming as Theory Building is the spine of this one, and it's held up better than almost anything else written about software since: a program is a theory held by the people who built it. The code and the documentation are a trace of that theory, not the theory itself. "The death of a program," Naur wrote, "happens when the programmer team possessing its theory is dissolved." By that definition, a vibe-coded app is dead on arrival — the theory never formed in a human head to begin with. The bus factor doesn't count down from some healthy number. It starts at zero on merge day, because the architectural intent lived in the prompts, and the prompts are gone.

In the traditional loop, code is a byproduct of understanding. In the vibe loop, code is a byproduct of a prompt — and the prompt is the part that gets thrown away.

Rubber-stamp review is how this spreads. When AI output volume outpaces a reviewer's ability to re-derive the intent behind it, review degrades into "looks plausible" — a documented pattern called automation bias, measured at 26% higher acceptance of erroneous recommendations when the recommendation comes with the appearance of authority. Six months later you're an archaeologist in a codebase with your own name on every commit.

Tests don't rescue you here, and it's worth being explicit about why: they were written by the same model, from the same misunderstanding, so they tend to confirm what the code does rather than specify what it should do. Ninety percent coverage with zero confidence is a completely normal outcome — coverage measures lines executed, not intent verified. The practical split is to write the contract tests at the boundary yourself, where the actual specification lives, and let an agent fill in the unit tests underneath that boundary.

High coverage and low confidence aren't opposites — they're a common outcome when the tests share the same blind spot as the code.

The evidence for the comprehension gap is uncomfortable reading. A 2025 randomised controlled trial from METR had 16 experienced open-source developers complete 246 real tasks using Cursor and Claude — and found AI assistance made them 19% slower, while they'd forecast being 24% faster and believed, after the fact, that they had been roughly 20% faster. It's the cleanest measurement available of confident miscalibration about one's own AI-assisted work. DORA's 2024 report found the aggregate signature at organisation scale: 25% more AI adoption correlated with a 1.5% drop in throughput and a 7.2% drop in delivery stability — individual flow feels great, and the shared system degrades anyway, which is exactly what you'd expect when nobody's holding the theory of how it fits together. Separately, a comprehension quiz found engineers who used AI to generate code scored 50% on questions about that code, against 67% for engineers who'd used AI only for Q&A while writing it themselves.

Every other item in this series is a fixable engineering problem. This one is different, because it removes your ability to fix the others: if nobody can explain how the data model got tangled or why the queue isn't idempotent, nobody can fix it with confidence either. The fix is unglamorous — architecture decision records for anything structural, a written system narrative a new engineer reads on day one — but the rule that does the most work in the entire series is simpler than any of that: if you can't explain how it works, you don't merge it. The agent can write the code. You still have to own the theory.

If you've shipped fast with AI tools and want a second pair of eyes before it goes further, that's exactly what a vibe code audit is for.
